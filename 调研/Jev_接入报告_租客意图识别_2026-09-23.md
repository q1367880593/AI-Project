# Jev 接入报告：租客聊天意图识别

> 版本：V1.0  
> 日期：2026-09-23  
> 范围：**只讨论意图识别**，不包含客户分类、需求槽位抽取、留资判断、质检评分。  
> 基线文件：《租客消息识别 Prompt V3.0.1》

---

# 0. 先说结论

建议采用：

```text
当前轮租客消息 + 必要历史上下文
                  ↓
        Jev：72 个 Noul，一次请求
                  ↓
          72 个意图概率
                  ↓
       业务规则后处理 / 阈值
                  ↓
             最终 intents
```

**第一版不要做 72 次 HTTP 调用。**

Jev 的设计允许同一个 `state` 携带多个 questions，多个 Noul 可以在一个 request 中并行计算。这样“72 个 Noul”在网络层面仍是 **1 次 API 请求**。citehttps://learnjev.com/tutorials/three-primitives

同时建议保留一个级联版本：

```text
Jev 高置信
   ↓
直接采用

Jev 低置信 / 冲突 / 特殊 case
   ↓
现有 LoRA
   ↓
仍不确定
   ↓
在线大模型
```

# 1. 当前意图识别的真实基线

## 1.1 当前 Prompt 的任务形态

V3.0.1 当前意图识别部分定义的是：

```text
输入：
conversation_history
+
current_round.tenant_messages

输出：
0~N 个 intent
```

历史上下文的作用是理解：

- 省略
- 指代
- 身份延续
- “可以 / 是的 / 不行 / 哪个 / 我加你”等短回复

但历史消息本身不能直接作为当前轮意图输出。fileciteturn1file0

## 1.2 当前是多标签，不是单标签

V3.0.1 明确规定同一轮可以同时输出多个意图，并要求去重、按首次出现顺序输出。典型规则包括：

```text
“这个月租金多少钱？最低多少？”
→ RENT_PRICE_AND_PAYMENT
→ PRICE_NEGOTIATION
```

以及：

```text
“还有三居吗？最好离国贸近一点。”
→ REQUEST_OTHER_PROPERTIES
→ STATE_RENTAL_NEEDS
```

fileciteturn1file0

## 1.3 当前 Prompt 实际为 72 个唯一 intent

V3.0.1 的“72 个可选意图全集”实际包含 72 个唯一 `intent_id`。本报告以这 72 个为 Jev 第一版 POC 的标签集。fileciteturn1file0

> 说明：业务此前口径如果存在“82 类”，则必须在真正上线前把线上最新 label dictionary 与 V3.0.1 对齐；本报告不自行补造那 10 类。

# 2. Jev 的正确建模方式

## 2.1 不建议：72 类 Choice 直接替换

Choice 的本质是：

```text
72 个候选
   ↓
选一个
```

而我们需要：

```text
A=true
B=true
C=false
D=false
...
```

因此直接做一个 72-way Choice 会丢失多意图能力。

### Choice 可以留作对照组

POC 可以额外测一个：

```text
72-way Choice
```

目的不是上线，而是回答：

> 如果只保留一个主意图，Jev 的单标签能力如何？

这可以作为 benchmark baseline。

---

## 2.2 第一版主方案：72 Noul

一个 request：

```json
{
  "model": "jev-latest",
  "state": {"conversation_history": [], "current_round": {"tenant_messages": []}},
  "questions": {
    "PROPERTY_AVAILABILITY": {
      "type": "noul",
      "instructions": "当前轮租客消息是否表达当前房源是否仍在出租的询问？"
    },
    "PROPERTY_AVAILABLE_INVENTORY_QUERY": {
      "type": "noul",
      "instructions": "当前轮租客消息是否在查询当前房源可租库存或还有几套/哪间可租？"
    },
    "...": {
      "type": "noul",
      "instructions": "..."
    },
    "UNKNOWN": {
      "type": "noul",
      "instructions": "当前轮消息是否为空、乱码、纯符号或无法结合上下文理解？"
    }
  }
}
```

返回：

```json
{
  "answers": {
    "PROPERTY_AVAILABILITY": {"type":"noul", "noul":0.03},
    "RENT_PRICE_AND_PAYMENT": {"type":"noul", "noul":0.92},
    "PRICE_NEGOTIATION": {"type":"noul", "noul":0.88}
  },
  "usage": {
    "input_tokens": 8120,
    "output_tokens": 0
  }
}
```

实际字段以接入时官方 API/SDK 为准；这里展示的是逻辑形态。

Jev 官方介绍和公开 API 资料都强调：同一个 state 可以携带多个问题，并行得到多个判断结果。citehttps://learnjev.com/tutorials/three-primitiveshttps://typesafe.ai/blog/introducing-system-one-models-and-jev

# 3. 当前 Prompt 不应该原样搬过去

当前 Prompt 里存在三类东西：

## 3.1 A 类：真正需要模型判断的“语义问题”

例如：

```text
这句话是不是在议价？
这句话是不是在问看房？
这句话是不是在询问电梯？
```

这些交给 Jev。

## 3.2 B 类：确定性业务规则

例如：

```text
如果已有其他意图
→ 删除 GENERAL_CONVERSATION
```

或者：

```text
“最低多少”
→ RENT_PRICE_AND_PAYMENT + PRICE_NEGOTIATION
```

这类逻辑不要再交给模型，直接代码处理。

## 3.3 C 类：输出整理

例如：

```text
同一意图去重
按首次出现顺序排序
evidence_message_ids 去重
```

也应该放在代码层。

因此最终应该从：

```text
超长 Prompt
```

变成：

```text
Jev = Semantic Decision Engine

Code = Business Policy / Post Processor
```

# 4. 72 个 Noul 的 Question 怎么写

## 4.1 推荐统一模板

每个 intent 不要只写标签名，而要写“判断契约”：

```text
当前轮租客消息是否表达以下意图：
【INTENT_ID】
业务定义

只判断当前轮租客消息。
历史上下文只用于解决当前轮中的省略、指代和短回复。
当前轮没有足够证据时判断为 false。
```

## 4.2 示例

### PRICE_NEGOTIATION

```text
当前轮租客消息是否表达议价诉求？
包括询问能否降价、能否优惠、价格是否还能谈、认为价格过高、提出目标租金等。
只判断当前轮；历史只用于理解当前轮的省略和上下文。
```

### RENT_PRICE_AND_PAYMENT

```text
当前轮租客消息是否询问租金金额、付款方式、付款周期、月付/季付/年付或交租时间？
只判断当前轮；历史只用于理解当前轮的省略和上下文。
```

### VIEWING

```text
当前轮租客消息是否表达看房诉求？
包括提出看房、询问/确认看房时间地点、赴约、正在前往/已经到达、为看房询问钥匙，以及为碰面提供当前位置。
只判断当前轮；历史只用于理解当前轮的省略和上下文。
```

# 5. 重点 Case 设计

下面这些 Case 应直接进入 POC Hard Set。

## Case 01：单意图——租金

```text
租客：多少钱一个月？
```

期望：

```text
RENT_PRICE_AND_PAYMENT
```

关键验证：不要误判成 `PRICE_NEGOTIATION`。

---

## Case 02：单意图——议价

```text
租客：还能便宜吗？
```

期望：

```text
PRICE_NEGOTIATION
```

关键验证：不要把所有“价格相关”都打成 `RENT_PRICE_AND_PAYMENT`。

---

## Case 03：双意图——价格 + 议价

```text
租客：这个月租金多少钱？最低多少？
```

期望：

```text
RENT_PRICE_AND_PAYMENT
PRICE_NEGOTIATION
```

这是最重要的多标签 Case 之一。

---

## Case 04：需求 + 推荐

```text
租客：还有三居吗？最好离国贸近一点。
```

期望：

```text
REQUEST_OTHER_PROPERTIES
STATE_RENTAL_NEEDS
```

关键验证：推荐场景里的“三居”“离国贸近”是筛选条件，不应被错误识别成当前房源属性询问。

---

## Case 05：需求门槛，不是拒绝

```text
租客：6楼已经是极限。
```

期望：

```text
STATE_RENTAL_NEEDS
```

关键验证：不要误判 `REJECT_CURRENT_PROPERTY`。

---

## Case 06：拒绝当前房源

```text
租客：这个房子太小了，算了。
```

期望：

```text
REJECT_CURRENT_PROPERTY
```

关键验证：这是对当前房源的拒绝，不是普通聊天。

---

## Case 07：短回复 + 上下文

历史：

```text
经纪人：明天下午 3 点带您看，可以吗？
```

当前轮：

```text
租客：可以
```

期望：

```text
VIEWING
```

关键验证：Jev 能否正确利用 history，还原短句含义。

---

## Case 08：联系经纪人

```text
租客：你给我个电话，我加你。
```

期望：

```text
REQUEST_AGENT_OR_HUMAN
```

不要误打：

```text
PROVIDE_TENANT_CONTACT
```

因为租客没有提供自己的联系方式。

---

## Case 09：距离 + 周边

```text
租客：离国贸多远？附近有地铁吗？
```

期望：

```text
DISTANCE_TO_DESTINATION
NEARBY_SURROUNDINGS_QUERY
```

关键验证：两个语义方向都要保留。

---

## Case 10：短租

```text
租客：可以短租吗？
```

期望：

```text
LEASE_TERM_QUERY
STATE_RENTAL_NEEDS
```

这是当前 Prompt 的显式业务规则，应作为 hard case。

---

## Case 11：电梯条件

```text
租客：这套有电梯吗？
```

期望：

```text
PROPERTY_ELEVATOR
STATE_RENTAL_NEEDS
```

因为现有 Prompt 把“询问某筛选条件能否满足”同时视为需求表达。fileciteturn1file0

---

## Case 12：业务外问题

```text
租客：这个小区物业公司是哪家？
```

如果不落入当前 72 类，应：

```text
OTHER_QUESTION
```

关键验证：不要为了追求覆盖率强行套入相近标签。

---

## Case 13：纯聊天

```text
租客：好的，谢谢。
```

在没有其他业务意图时：

```text
GENERAL_CONVERSATION
```

若同轮已经存在其他业务意图，则应删除 `GENERAL_CONVERSATION`。

---

## Case 14：未知

```text
租客：￥#@……
```

无法结合上下文还原时：

```text
UNKNOWN
```

# 6. 请求次数：72 Noul 到底是不是 72 次调用

## 6.1 生产建议：1 次请求

```text
HTTP Request #1
 ├── Q1 Noul
 ├── Q2 Noul
 ├── Q3 Noul
 ├── ...
 └── Q72 Noul
```

因此：

> **网络层：1 次请求。**

不是：

```text
HTTP #1 → Q1
HTTP #2 → Q2
...
HTTP #72 → Q72
```

公开资料明确描述：同一个 request 的 questions 共享 state，并行评估，没有必要拆开发送。citehttps://learnjev.com/tutorials/three-primitives

# 9. Threshold 怎么定

这是整个项目最关键的参数之一。

Jev Noul 返回的是：

```text
P(intent = true)
```

它不是 72-way softmax。

因此不能做：

```text
取最大概率的 intent
```

而应该做：

```text
P(intent) >= threshold
→ 认为命中
```

例如：

```text
RENT_PRICE_AND_PAYMENT 0.94
PRICE_NEGOTIATION       0.90
VIEWING                 0.12
```

若阈值 0.80：

```text
输出 A + B
```

而不是只输出 A。

公开资料明确指出，多个 Noul 的概率可以分别成立，并不会像互补 softmax 一样要求总和为 1。citehttps://learnjev.com/tutorials/three-primitives

# 10. 阈值建议：不要一个阈值打天下

第一版可以测试：

```text
0.50
0.60
0.70
0.75
0.80
0.85
0.90
0.95
```

对每个阈值统计：

```text
Precision
Recall
F1
Coverage
Fallback Rate
```

最终可能得到：

```text
高风险/高成本意图
→ 0.90

普通意图
→ 0.80

低风险辅助意图
→ 0.70
```

具体阈值必须由人工标注数据决定，不建议直接采用 0.8/0.9 这类拍脑袋参数。

# 12. Benchmark 数据集怎么建

## 12.1 第一版建议

建议先拿 **1 万条真实历史会话** 做人工 Gold Set。

不建议随机抽 1 万条后直接结束，而应该做分层采样：

```text
热门意图
+
低频意图
+
多意图
+
短上下文
+
强上下文
+
历史省略
+
规则 hard case
```

如果某些冷门 intent 只有几十条，必须补采样，否则总体 Accuracy 会掩盖问题。

## 12.2 必须单独做 Hard Set

建议至少 1,000 条：

```text
价格边界
拒绝 vs 需求门槛
请求推荐 vs 房源属性查询
看房 vs 普通聊天
物业位置 vs 到目标地点距离
联系方式索要 vs 提供联系方式
GENERAL_CONVERSATION vs OTHER_QUESTION
UNKNOWN vs COMMUNICATION_FAILURE
```

# 13. Evidence 怎么处理

现有输出要求里还有：

```text
evidence_message_ids
```

第一版不建议让 72 个 Noul 直接返回消息 ID。

建议：

```text
第一阶段
Jev：判断 intent 是否成立

第二阶段
只对已命中的 intent
逐条消息做 evidence 判断

最后
代码组装 evidence_message_ids
```

这样可以避免让一个判断问题承担太多输出任务。

> 注意：本报告仍只研究“意图识别”，evidence 只是为了兼容现有结果结构，不把它扩展成另一个独立业务任务。

# 17. 最终落地建议

## 第一阶段：不改现网

```text
真实流量
  ├─ 现网结果
  └─ Jev Shadow
```

只记录差异。

## 第二阶段：离线阈值校准

```text
人工 Gold Set
   ↓
threshold sweep
   ↓
确定每个 intent / 组的阈值
```

## 第三阶段：小比例级联

```text
Jev
↓
高置信直接采用
↓
低置信 LoRA
↓
极少数再到在线 LLM
```

## 第四阶段：逐步替换在线 LLM

只有当：

```text
准确率稳定
+
fallback 可控
+
延迟稳定
+
成本稳定
+
错误样本可解释
```

才扩大流量。
